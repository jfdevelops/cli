An addon is an integration recorded in `jfdevelops.json`. The skills its package publishes are offered only once the addon is enabled. Run these commands in a configured project: you need `jfdevelops.json` (run `npx @jfdevelops/cli init` first) and a terminal; see [command requirements](commands.md#command-requirements).

In this guide you will:

- Choose an addon.
- Adopt or install it.
- Enable the skills it publishes.
- Set up the docs addon.

## Choose an addon

| Addon name | Package | Installed as | What it adds |
| --- | --- | --- | --- |
| `convex` | `convex` | Dependency | Convex backend |
| `portless` | `portless` | Development dependency | Named local development URLs |
| `docs` | `@jfdevelops/docs` | Development dependency, at the project root | Versioned docs, navigation, and API reference |
| Any `@tanstack/*` or `@jfdevelops/*` library | The library itself | Dependency | The library and its skills |

`@jfdevelops/cli` and `@jfdevelops/skills` are not addons. To see what you can add, run:

```sh
jfdevelops add --list
```

## Adopt an installed integration

`init` detects installed integrations and preselects them for adoption. To adopt one later, run:

```sh
jfdevelops add addon convex
```

Pass the addon name or the package name, for example `jfdevelops add addon @jfdevelops/docs`. An integration whose package is already installed is not installed again, except the docs addon: when only a workspace package has `@jfdevelops/docs`, it is still installed at the project root.

## Install an addon

When the package is not installed, the command asks where to install it in a project with several packages (the docs addon always goes at the project root). It then shows the exact install command and asks you to confirm. After the install it reviews and records the changes.

If you cancel or a later step fails after the install, the package stays installed. Run `jfdevelops add addon <name>` again to finish, or uninstall the package.

## Enable addon skills

After the addon is adopted, the command offers the addon package's skills with every skill preselected. Skills from a detected integration that is not adopted stay hidden from `init`, `add`, and `skills`. Keep them current with `jfdevelops skills sync` or `jfdevelops skills update`; see [Skills](skills.md#sync-after-an-upgrade).

## Set up the docs addon

```sh
jfdevelops add addon docs
```

The command does the following:

1. Installs `@jfdevelops/docs` as a development dependency at the project root, when it is not there.
2. Asks which package the docs describe, only when the project has library packages besides the root.
3. Asks for the library name shown in the docs, defaulting to the title-cased last segment of the package name.
4. Records `{ "package": "<directory>", "name": "<name>" }` as the addon's options in `jfdevelops.json`.
5. Adds the `docs:generate` and `docs:check` scripts, keeping any existing script with the same name.
6. Adds `docs/docs.json` and `docs/**/meta.json` to `.gitignore` under `# Generated by @jfdevelops/docs`.
7. Starts `docs/README.md` when it does not exist.
8. Adds `.github/workflows/docs.yml`.

The workflow runs on pull requests, and on pushes to `main`, that change `docs/**`, the documented package's `src/**`, `package.json`, or `CHANGELOG.md`, `jfdevelops.json`, or the workflow itself. It sets up your package manager (Bun with `oven-sh/setup-bun`, otherwise Node.js 24), installs from the lockfile, then runs `docs:generate` and `docs:check`. The addon owns the workflow, so local edits to it go through conflict review; see [Conflicts](skills.md#conflicts).

## Finish an unfinished docs setup

When `init` adopts the `docs` addon, or a setup step fails, the addon is recorded without options. Run `jfdevelops add addon docs` again to finish it.
